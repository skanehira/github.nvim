## UC-001: 導入して利用を開始する

### 概要

| 項目 | 内容 |
| --- | --- |
| ユースケースID | UC-001 |
| ユースケース名 | 導入して利用を開始する |
| 主アクター | 開発者 |
| 副アクター | Neovim、GitHub CLI（gh） |
| トリガー | 開発者がgithub.nvimを導入し、NeovimからIssue操作を始める。 |

### 事前条件

- 開発者がNeovimへプラグインを追加できる。
- 正常系ではghが導入され、対象のGitHubへアクセスできる認証が完了している。ghが未導入・未認証の場合は例外フローE1で扱う。
- Denops、Deno、Actions向けのYAML解析、Telescopeは導入の前提条件に含めない。

### 事後条件

- Neovimが起動し、github.nvimのIssue操作の入口を利用できる。
- GitHubへ通信する操作はghを通じて開始される。
- ghの準備が不足している場合もNeovimでの通常の編集を継続でき、Issue操作を試みた時点で不足する準備が分かる。

### 正常系フロー

| --- | --- | --- |
| 1 | 開発者 | github.nvimをNeovimへ追加する。 |
| 2 | 開発者 | 必要な設定を登録し、Neovimを起動する。設定を省略した項目には既定値を使う。 |
| 3 | github.nvim | Issue操作の入口を利用可能にする。 |
| 4 | 開発者 | `:edit github://owner/repo/issues`で対象リポジトリのIssue一覧を開く。 |
| 5 | github.nvim | このGitHub操作に必要なghの準備状況を確認する。 |
| 6 | github.nvim | ghを使って指定先へのIssue操作を開始し、UC-002の一覧表示へ進む。 |

## UC-002: Issueを一覧・検索し、本文を確認する

### 概要

| 項目 | 内容 |
| --- | --- |
| ユースケースID | UC-002 |
| ユースケース名 | Issueを一覧・検索し、本文を確認する |
| 主アクター | 開発者 |
| 副アクター | GitHub（ghを通じてアクセスする） |
| トリガー | 開発者が対象リポジトリのIssueを確認・検索したい。 |

### 事前条件

- github.nvimのIssue操作の入口を利用でき、ghの導入・認証が完了している。
- 対象のownerとrepoを指定できる。
- 正常系では、対象リポジトリへの閲覧権限があり、GitHubへ通信できる。

### 事後条件

- 指定したリポジトリと検索条件に一致するIssueが、最大30件表示されている。
- 各Issueの番号・タイトル・状態・担当者・ラベル・コメント総数を確認できる。
- プレビューを実行した場合、一覧を残した縦分割の窓でカーソル行の本文を確認できる。
- 検索先と検索条件は一覧ごとに保持され、別の一覧や作業ディレクトリの変更の影響を受けない。

### 正常系フロー

| # | アクター | アクション |
| --- | --- | --- |
| 1 | 開発者 | `:edit github://owner/repo/issues`でIssue一覧を開く。 |
| 2 | github.nvim | 対象リポジトリと初期検索条件`state:open`を、その一覧の条件として保持する。 |
| 3 | github.nvim | ghを使って条件に一致するIssueを最大30件取得する。 |
| 4 | github.nvim | 各Issueの番号・タイトル・状態・担当者・ラベル・コメント総数を表示する。 |
| 5 | 開発者 | `ghs`で検索欄を開き、条件を入力してEnterで確定する。 |
| 6 | github.nvim | 同じリポジトリ内を検索し、操作した一覧の条件と結果を更新する。 |
| 7 | 開発者 | 確認したいIssueへカーソルを移動し、`K`を押す。 |
| 8 | github.nvim | カーソル行の取得済み本文を、一覧を残した縦分割の窓に表示する。 |

| 1b | github.nvim | 対応する`github://owner/repo/issues`の一覧として開く。 |

→ ステップ2へ進む。

### ビジネスルール

| ID | ルール |
| --- | --- |
| BR-006 | 公開URIは`github://owner/repo/issues`を使う。対応するGitHubのHTTPS URLも同じ一覧への入口として扱う。 |
| BR-007 | 新規に開いた一覧の初期条件は`state:open`とする。1回の一覧表示は最大30件で、ページ送りは今回の対象に含めない。並び順はGitHub検索の返却順に従う。 |

| BR-010 | コメント数にはGitHub上のコメント総数を表示する。取得済みコメント本文の件数を総数の代わりにしない。 |
| BR-011 | プレビューはカーソル行の1件を対象とし、一覧取得時点の本文を表示する。複数選択の印がある場合も、プレビュー対象はカーソル行である。 |
| BR-012 | 検索失敗時は直前の成功結果とその条件を保持する。該当0件は成功結果として扱い、以前の結果を0件表示へ置き換える。 |
| BR-013 | 取得結果は、操作した一覧とその最新の検索にだけ反映する。先行した検索の遅い応答や、閉じた一覧への応答で他の表示を更新しない。 |

### 受け入れ基準

- [ ] （US-002）認証済みでリポジトリの`github://`形式URIまたは対応するGitHub URLを開くと、未完了Issueが最大30件表示される。
- [ ] （US-002）Issue一覧を開くと、各Issueの番号・タイトル・状態・担当者・ラベル・GitHub上のコメント総数が表示される。
- [ ] （US-003）一覧で`ghs`を実行して検索条件を入力しEnterで確定すると、開いたリポジトリ内のIssueに絞った検索結果がその一覧へ表示される。
- [ ] （US-003）検索に成功した一覧を再読み込みすると、その一覧の検索条件を維持した結果が表示される。
- [ ] （US-004）Issue一覧でカーソル行の`K`を実行すると、取得済みの本文が一覧を残した縦分割の窓に表示される。
- [ ] （US-002）検索に一致するIssueがないときに一覧を取得すると、以前のIssue行に代わって0件であることが表示される。
- [ ] （US-003）検索または取得に失敗すると、失敗理由が表示され、直前の成功結果がある場合はその結果と検索条件が保持される。
- [ ] （US-002）一覧を開いた後に作業ディレクトリを変えて検索または再読み込みを行っても、その一覧で指定したリポジトリの結果が表示される。
- [ ] （US-003）検索条件を続けて変更して新しい検索が先に完了した後で古い応答が届いても、表示は新しい検索結果のまま維持される。
- [ ] （US-003）検索条件の入力をキャンセルすると、新しい検索を開始せず、直前の成功結果と検索条件が維持される。
- [ ] （US-003）検索中の一覧を閉じた後で応答が届いても、その一覧は再作成されず、別の画面も更新されない。

## UC-003: Issueを作成する

### 概要

| 項目 | 内容 |
| --- | --- |
| ユースケースID | UC-003 |
| ユースケース名 | Issueを作成する |
| 主アクター | 開発者 |
| 副アクター | GitHub、GitHub CLI（gh） |
| トリガー | 開発者が指定したリポジトリへ新しいIssueを作成したい。 |

### 事前条件

- github.nvimのIssue操作の入口を利用でき、ghの導入・認証が完了している。
- 対象リポジトリのownerとrepoを指定できる。
- 正常系では、そのリポジトリでIssueを作成する権限があり、GitHubへ通信できる。

### 事後条件

- 正常終了した場合、入力した内容のIssueが指定したリポジトリへ作成され、作成先のURLを確認できる。
- 成功後は、作成したIssueの編集、URLコピー、ブラウザ起動の次操作を選べる。
- 作成処理をキャンセルした場合や失敗した場合、入力済みの本文が残り、結果を確認できる。
- 作成処理中の追加保存によって、同じ作成操作が二重送信されない。

### 正常系フロー

| # | アクター | アクション |
| --- | --- | --- |
| 1 | 開発者 | Issue一覧で`ghn`を実行するか、`:edit github://owner/repo/issues/new`で作成を開始する。 |
| 2 | github.nvim | 作成対象のリポジトリを保持し、利用できるMarkdownテンプレートと空の本文の選択肢を表示する。 |
| 3 | 開発者 | テンプレートまたは空の本文を選ぶ。 |
| 4 | github.nvim | 選択したテンプレートの本文、または空のMarkdown編集バッファを開く。 |
| 5 | 開発者 | 本文を編集し、`:write`を実行する。 |
| 6 | github.nvim | 本文と作成対象のリポジトリをghへ渡し、ghの対話画面を開く。 |
| 7 | 開発者 | ghの対話画面でタイトルなどを入力し、Issueの作成を完了する。 |
| 8 | github.nvim | 作成成功と作成先URLを確認して対話画面を閉じ、編集・URLコピー・ブラウザ起動の選択肢を表示する。作成開始後に本文の変更がなければ本文バッファも閉じ、変更があれば未送信の内容として残す。 |
| 9 | 開発者 | 次の操作を選ぶか、選択を終了する。 |

編集はUC-004、URLコピーはUC-011、ブラウザ起動はUC-010へ進む。次の操作を選ばずに終了しても、作成済みのIssueは維持される。

### 代替フロー

#### A: 空の本文から作成する（ステップ3の代替）

| # | アクター | アクション |
| --- | --- | --- |
| 3a | 開発者 | 空の本文を選ぶ。テンプレートがないリポジトリでも、この選択肢を利用する。 |
| 3b | github.nvim | 空のMarkdown編集バッファを開く。 |

→ ステップ5へ進む。

#### B: テンプレートの選択をキャンセルする（ステップ3）

| # | アクター | アクション |
| --- | --- | --- |
| 3a | 開発者 | テンプレートの選択をキャンセルする。 |
| 3b | github.nvim | Issueを作成せずに選択を終了する。既存の編集中の内容を上書きしない。 |

→ 作成を終了する。

#### C: 作成処理中に再度保存する（ステップ6・7）

| # | アクター | アクション |
| --- | --- | --- |
| 6a | 開発者 | ghでの作成処理が完了する前に、同じ本文バッファで再度`:write`を実行する。 |
| 6b | github.nvim | 処理中であることを案内し、進行中の作成操作を継続する。追加の作成処理は開始しない。 |

→ ステップ7または8の完了を待つ。

#### D: 作成処理中に本文を編集する（ステップ6・7）

| # | アクター | アクション |
| --- | --- | --- |
| 6a | 開発者 | ghでの作成処理が完了する前に、元の本文バッファを編集する。 |
| 6b | github.nvim | 作成には送信開始時点の本文を使い、作成後もその後の編集を未送信の内容として保持する。自動で別のIssueを作成しない。 |

→ ステップ8へ進み、作成に使われた本文と未送信の編集を区別して案内する。

## 設計判断の根拠

- 編集の同時更新は、移植元と同じくGitHubが最後に受け付けた値を正とし、独自の競合制御を追加しない。更新する項目を限定し、無関係な項目の巻き戻しを防ぐ。
- 関連PR取得では原本の公開引数形式を保ち、明示対象でもGit checkoutを必須にしていた原本の制約を取り除く。
- 初期版の状態はバッファ・機能・リポジトリ単位で保持する。レビューの永続セッションやworktreeの移行は将来の統合で扱う。
- 作成・投稿・更新は送信時点の入力を対象とし、応答待ちの間の編集を未送信・未保存の内容として保持する。初回取得の失敗を空の現在値に変換しないことで、取得失敗による意図しない解除・上書きを防ぐ。
