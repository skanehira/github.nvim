# Issueの状態変更

- 種別: 機能設計書
- 対象 UC: UC-005 (docs/design/USECASES.md)

## 何を作るか

UC-005の利用者操作を実現する。対象規則はBR-025, BR-026, BR-027。認証・実行・リポジトリ文脈と非同期の共通規約はDESIGN.md「横断規約」に従う。

## 入出力と振る舞い

- `<C-j>`/`<C-k>`はカーソル行の選択印をトグルして次/前行へ移動する。端では移動しない。再取得開始時は選択を解除する。
- `ghc`はクローズ、`gho`は再オープンする。選択行があればその集合、なければカーソル行1件を処理開始時に固定する。
- 一覧から固定した各IssueのGraphQL node IDを受け取り、IDが取得できない対象は個別に理由を報告して送信しない。各Issueの状態変更を個別に送信し、成功・失敗・結果未確認を対象ごとに記録して通知する。成功分を失敗分のために取り消さない。
- 完了後は元一覧を最後に成功した検索条件で再取得する。再取得失敗は状態変更の成否と区別する。対象なしでは要求しない。

正常系の操作:

| # | アクター | アクション |
| --- | --- | --- |
| 1 | 開発者 | 必要に応じて`<C-j>`・`<C-k>`でIssueを選択する。 |
| 2 | 開発者 | `ghc`でクローズ、`gho`で再オープンを実行する。 |
| 3 | github.nvim | 選択済みのIssueを対象とし、選択がなければカーソル行の1件を対象とする。 |
| 4 | github.nvim | 各対象の状態をgh経由で変更し、対象ごとの結果を記録する。 |
| 5 | github.nvim | 成功・失敗を案内し、開いている元の一覧を同じ検索条件で再取得する。 |

代替フロー:

- A1: 単一Issueでも複数Issueでも同じ操作を使う。
- A2: すでに目的の状態である場合も、その状態へ設定できたことを成功として扱う。
- A3: 検索条件から外れた成功済みIssueは、再取得した一覧には表示されない。
- A4: 処理中に元の一覧を閉じた場合も結果は案内するが、その一覧を再作成しない。

例外フロー:

- E1: 対象がない場合は案内を表示し、状態変更を開始しない。
- E2: 一部だけ失敗した場合は成功分を取り消さず、失敗したIssueと理由を案内する。再取得に失敗しても状態変更の成功と混同しない。

## API

GraphQL updateIssueのid/stateを指定する。すでに目的状態の場合も成功として扱う。書込みの自動再送は行わない。DESIGN.md「GitHub API一覧」「横断規約」参照。

## 実装の配置

| 処理 | 層 | 実装先ファイル |
| --- | --- | --- |
| Issueの状態変更の状態・操作・表示 | 機能 | `lua/github/features/issues/state.lua` |
| Issueの状態変更の振る舞いの検証 | テスト | `lua/github/features/issues/state_spec.lua` |

共通URI・プロセス・repo文脈の実装はfoundation設計に属し、操作固有コードは本機能が所有する。実行器・時刻・外界は注入する。各ファイルは実装時に作成する計画であり、現時点では存在しない。

## エッジケースの決定

- 空: 対象なしは案内し更新しない。
- 境界: 単一・複数・すでに目的状態の場合を扱う。
- エラー: 対象ごとに成功と失敗を表示し、成功分を維持する。
- 並行: 開始時の対象とrepoを固定し、cursor/cwdの変更に追従しない。
- 再表示: 同じ検索条件で再取得を開始した時に選択を解除し、取得失敗を更新失敗と混同しない。
