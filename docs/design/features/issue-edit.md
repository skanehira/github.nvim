# Issueタイトル・本文・ヘッダー編集

- 種別: 機能設計書
- 対象 UC: UC-004 (docs/design/USECASES.md)

## 何を作るか

UC-004の利用者操作を実現する。Issue本文の画面は、本文の上にGitHubのIssue画面に近いヘッダーを置き、タイトル・担当者・ラベル・Projects v2のProjectとStatusをそのまま編集できるようにする。状態（Open/Closed）・番号・リポジトリは読み取り専用の仮想行として表示する。対象規則はBR-021, BR-022, BR-023, BR-024。認証・実行・リポジトリ文脈と非同期の共通規約はDESIGN.md「横断規約」に従う。

## 入出力と振る舞い

- 一覧の`ght`でカーソル行の1行タイトル、`ghe`または`github://owner/repo/issues/<number>`でヘッダーとMarkdown本文を開く。`ghe`は選択印があれば解除を案内する。
- 本文画面の実バッファ行は先頭に次の4行を置く。1行目はタイトル、2行目は`Assignees   @user, ...`、3行目は`Labels      <pill>, ...`、4行目は`Projects    <Project>  ·  <field>: <value>, ...`。値がない行は`—`を出す。5行目以降は本文。
- 状態（● Open/Closed）・`#number`・`owner/repo`は1行目の上、区切り線は4行目の下に仮想行として表示する。仮想行はウィンドウ幅に合わせて折り返し、実バッファ行と本文は`wrap`で表示する。仮想行は`:write`では送らない。
- ヘッダーの各項目はそのまま編集できる。保存時はバッファ全体をヘッダーとして解析し、変更のあった項目だけを送る。
  - タイトル: 1行。空白のみは拒否する。制御文字は表示時に空白へ正規化する。
  - 担当者: カンマ区切り。`@`は省略できる。大文字小文字を区別せず解決し、重複は1件にまとめる。10件を超える入力は拒否する。
  - ラベル: カンマ区切り。ピル（`\u{E0B6}`/`\u{E0B4}`）は表示だけに使い、解析時は取り除く。名前は完全一致で解決し、暗黙作成しない。
  - Projects: カンマ区切り。`<Project>`または`<Project>  ·  <field>: <value>`を書く。`<Project>`だけなら追加、`<field>: `の値が空なら解除、値があれば単一選択フィールドを更新する。Project名は完全一致で解決する。
- 変更のない`:write`は送信しない。変更がある`:write`は、updateIssue（タイトル・本文・担当者・ラベル）とProjectsのmutation（項目追加・削除・フィールド更新・解除）を並列に送る。応答待ちに追記された内容は未保存として残し、失敗時は全入力を維持する。
- 2〜4行目で`<C-x><C-o>`を押すと、担当者・ラベル・Project名・Status値の入力補完を出す。候補は必要なときだけ取得し、リポジトリ単位で5分間キャッシュする。同じ取得が並行してもAPI呼び出しは1回にまとめる。ProjectsのStatus候補はProjectのフィールドを取得してから出す。
- ヘッダー行が4行未満、または各行のラベル名が欠けている場合は保存せず、行の復元を案内する。存在しない担当者・ラベル・Project・Status値は理由を表示し、入力を保持して送信しない。
- 取得成功後だけ編集と保存を許し、初回取得失敗の空bufferを保存可能にしない。本文は空を許す。
- 本文から`ght`・`ghm`・`gha`・`ghl`でタイトル・コメント一覧・担当者・ラベルへ進める。`gha`/`ghl`は一括置換の専用画面として残す。本文を開く際はedit/new/vnew/tabnewを選べる。タイトルは1行の横分割で開き、変更を保存できたら閉じる。送信後に追記があれば閉じず保持する。
- ヘッダ用のprojectItems取得には`project`スコープが必要。スコープ不足でクエリが失敗した場合はprojectItemsを含めないクエリで再取得し、Projects行を`—`にして本文と他のメタ情報は表示する。`:edit!`はIssueとヘッダを再取得する。

同一編集bufferの保存中に再度`:write`した場合は進行中と通知し、追加の保存要求を送らない。保存開始後の編集は未保存のまま残し、完了後に利用者が改めて保存できる。

正常系の操作:

| # | アクター | アクション |
| --- | --- | --- |
| 1 | 開発者 | 一覧の`ght`でカーソル行のタイトル、`ghe`または`github://owner/repo/issues/<number>`で本文を開く。 |
| 2 | github.nvim | 現在の対象項目とメタ情報を取得し、編集可能なヘッダーと本文を表示する。 |
| 3 | 開発者 | タイトル・担当者・ラベル・Projects・本文を編集して`:write`を実行する。 |
| 4 | github.nvim | 入力を解析して差分を検出し、対象リポジトリ・Issue・項目を固定してgh経由で保存する。 |
| 5 | github.nvim | 成功したことを案内し、ヘッダーを確定値で再描画する。保存開始後にも追記があれば、その追記は未保存の変更として残す。 |

代替フロー:

- A1: 本文を空にして保存した場合は、本文を空に更新する。
- A2: 本文編集の`ghe`は選択印がある場合に解除を案内する。タイトル編集はカーソル行の1件を対象にする。
- A3: 編集を閉じる際、未保存の変更はNeovimの通常の破棄操作で明示的に捨てた場合だけ破棄する。
- A4: ヘッダーの担当者・ラベル・Projectsをすべて`—`にして保存すると、対象項目を全解除する。
- A5: Projectsの行に`<Project>  ·  <field>: `（値が空）を書くと、そのフィールドを解除する。

例外フロー:

- E1: 空または複数行のタイトルは理由を表示し、入力内容を保持して保存を開始しない。
- E2: 権限・対象の不存在・通信などで保存が失敗した場合、理由を表示して編集内容を保持する。
- E3: 編集開始時の取得に失敗した場合は理由を表示し、取得できなかった項目を空の現在値として保存可能にしない。既存の未保存の入力があれば保持する。
- E4: ヘッダー行が欠けている場合は保存せず、復元する行を案内する。
- E5: 担当者が10件を超える場合、または存在しない担当者・ラベル・Project・Status値を指定した場合は理由を表示し、送信しない。

## API

GraphQL issue(number)で対象ID・number・title・state・body・assignees・labels・projectItemsを取得する。projectItemsは項目ID、ProjectのIDと名前、単一選択フィールドの名前・値・optionId・フィールドIDを取る。`project`スコープ不足のGraphQLエラーではprojectItemsを含めないクエリで再取得する。

updateIssueのinputにはidと変更項目だけを渡す。Projectsの変更は`addProjectV2ItemById`、`deleteProjectV2Item`、`updateProjectV2ItemFieldValue`、`clearProjectV2ItemFieldValue`を使う。担当者・ラベル・Projectの候補は`assignableUsers`、`labels`、`projectsV2`、`projectV2.fields`をpageInfoで全件取得し、リポジトリ単位で5分間キャッシュする。同じ取得が並行した場合はsingle-flightで1回のAPI呼び出しにまとめる。認証・エラー・同時編集の共通方針はDESIGN.md「横断規約」参照。

## エッジケースの決定

- 空: 空タイトルは拒否、空本文は保存できる。担当者・ラベル・Projectsの空行は全解除として扱う。
- 境界: 担当者は10件まで。タイトルは1行。ヘッダーは4行。本文はUTF-8と改行を保持する。
- ヘッダ: 値がないメタ情報は`—`。Closedは紫、Openは緑。仮想行はウィンドウ幅で折り返す。ラベルは色付きのピルで表示する。
- 不正値: 存在しない担当者・ラベル・Project・Status値は理由を表示し、入力を保持して送信しない。ラベルを暗黙作成しない。
- スコープ: projectItemsのスコープ不足は本文表示を妨げず、Projects行を`—`にする。
- エラー: 取得失敗で空の上書きを防ぎ、保存失敗で編集内容を維持する。
- 並行: 候補解決は並列、Projectsのmutationは並列に送る。GitHubが最後に受け付けた同一項目の保存を正とし、保存開始後の追記は未保存とする。
- 再表示: 未保存の変更を明示的な破棄なく再取得結果で置き換えない。保存成功後、未変更ならヘッダーを確定値で再描画する。
- キャッシュ: 候補はリポジトリ単位で5分間保持し、同じ取得の並行呼び出しを1回にまとめる。失敗した取得はキャッシュしない。
